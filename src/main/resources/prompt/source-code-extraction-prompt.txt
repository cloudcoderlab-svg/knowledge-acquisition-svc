ANTI-HALLUCINATION RULES FOR SOURCE CODE:
1. Extract ONLY from actual code, comments, and annotations - DO NOT infer business logic beyond what's explicitly implemented
2. DO NOT fabricate class names, method names, or variables that don't exist in the code
3. DO NOT assume business intent unless documented in comments, JavaDoc, or clear naming
4. Preserve EXACT naming - class names, method names, variable names, SQL table/column names
5. DO NOT invent database schemas, API contracts, or data structures not present in code
6. Empty arrays are acceptable - better than guessing non-existent entities
7. Use LOWER confidence (0.5-0.69) when inferring business purpose from code structure alone
8. Use HIGHER confidence (0.8-1.0) when business logic is documented in comments/annotations
9. When encountering TODO comments or incomplete code, note in knowledgeNotes, don't extract as complete entities
10. DO NOT extract test code, mock data, or example code as real business logic

=== SOURCE CODE EXTRACTION GUIDELINES ===

**Code Element to Entity Type Mapping:**

| Code Element | Extract As | Context |
|--------------|------------|---------|
| Class/Interface | solutionComponents | Implementation component (HOW) |
| Service Class | businessCapabilities | Business function (WHAT) if service layer |
| Controller/Endpoint | apis | REST/SOAP/RPC endpoints |
| Entity/Model/DTO | dataModels | Data structures, database tables |
| Validation logic | businessRules | Validation rules from code |
| if/switch/case business logic | businessRules | Business decision logic |
| Method with @Transactional | businessFlows | Workflow steps |
| Workflow/Process class | businessFlows | Complete workflows |
| Database table (SQL) | dataModels | Schema definitions |
| Foreign key (SQL) | relationships | Data relationships |
| API call to external system | integrations | External integrations |
| Role/Permission checks | businessRoles | Access control roles |
| Annotation metadata | businessPolicies | Governance, compliance |
| Configuration/Properties | deploymentResources | Environment resources |
| Method calls between classes | relationships | Component dependencies |

**Language-Specific Extraction Patterns:**

**Java/JSP:**
- Class annotations (@Service, @Component, @Controller, @RestController) → solutionComponents
- Method annotations (@GetMapping, @PostMapping, @RequestMapping) → apis
- @Entity, @Table annotations → dataModels
- Validation annotations (@NotNull, @Size, @Pattern) → businessRules with constraints
- Spring Security (@PreAuthorize, @Secured) → businessRoles
- JavaDoc comments → description fields (HIGH confidence)
- if/switch with business logic → businessRules (condition = code logic)
- Method parameters and return types → input/output for apis
- SQL queries in code → dataModels (extract table/column names)

**Python:**
- Class with methods → solutionComponents
- Flask/Django route decorators (@app.route, @api_view) → apis
- SQLAlchemy/Django models → dataModels
- Pydantic models → dataModels
- Docstrings → description fields (HIGH confidence)
- def function_name with business logic → businessFlows or businessRules
- Database migration files → dataModels with schema evolution

**PHP:**
- Class definitions → solutionComponents
- Laravel routes (Route::get/post) → apis
- Eloquent models → dataModels
- Middleware → businessPolicies (security, validation)
- PHPDoc comments → description fields

**SQL:**
- CREATE TABLE → dataModels (extract all columns, types, constraints)
- ALTER TABLE → schema evolution (note in knowledgeNotes)
- PRIMARY KEY → constraints in dataModels
- FOREIGN KEY → relationships between dataModels
- CHECK constraints → businessRules (validation type)
- Stored procedures → businessFlows (steps from procedure logic)
- Triggers → businessRules (event-driven rules)
- Views → dataModels (virtual tables)

**Oracle Forms (.fmb):**
- Form blocks → solutionComponents
- Form items → dataModels fields
- Triggers → businessRules or businessFlows
- LOV (List of Values) → businessTerms or reference data

=== CONFIDENCE SCORING FOR SOURCE CODE ===

**0.9-1.0 (Very High Confidence):**
- Entity explicitly documented with JavaDoc/docstring/comments explaining business purpose
- Method with clear business name AND comment AND implementation
- SQL table with column comments
- Example: `/** Validates customer credit limit before order approval */ public boolean validateCreditLimit(...)`

**0.7-0.89 (High Confidence):**
- Entity with descriptive naming suggesting business purpose
- Annotations providing business context
- Example: `@Service public class OrderApprovalService { ... }`

**0.5-0.69 (Medium Confidence):**
- Entity with minimal naming, business purpose inferred from code structure
- Example: `public void process(Order order) { if(order.total > limit) {...} }`

**Below 0.5 (Do Not Extract):**
- Test classes, mock implementations, example code
- Empty interfaces with no methods
- Utility classes with no business logic

=== EXTRACTION PRIORITY ORDER ===

1. **APIs** - Extract first to identify system boundaries
   - REST/SOAP endpoints (highest confidence from annotations/routes)
   - Method signatures → input/output parameters
   - Authentication/authorization → businessRoles

2. **Data Models** - Extract schema and entity definitions
   - Classes with @Entity, models, table definitions
   - Field names, types, constraints
   - Relationships (foreign keys, joins, references)

3. **Business Rules** - Extract validation and decision logic
   - Validation annotations/code
   - if/switch statements with business conditions
   - Calculated fields, business formulas

4. **Business Flows** - Extract workflows from code
   - Service methods orchestrating multiple steps
   - Transaction boundaries
   - State machines, process flows

5. **Solution Components** - Extract implementation classes
   - Services, controllers, utilities
   - Distinguish capability (WHAT business function) from component (HOW implemented)

6. **Integrations** - Extract external system calls
   - HTTP client calls, message queue producers
   - External API invocations

7. **Relationships** - Extract dependencies
   - Method calls between classes
   - Database foreign keys
   - API dependencies

=== CRITICAL RULES ===

IMPORTANT: dataModels do NOT have a confidence field - do not include it in the output

**Schema v2 Compliance:**
1. Use `solutionComponents` (HOW implemented) vs `businessCapabilities` (WHAT business function)
2. Embed business context in `trigger`, `outcome`, `condition` fields (see format above)
3. Use `ruleType` NOT deprecated `ruleCategory`
4. DO NOT use deprecated fields: `businessPurpose`, `businessValue`, `businessCriticality`, `businessFrequency` (embed in trigger/outcome instead)
5. DO NOT use deprecated fields: `businessRationale`, `businessImpact` (embed in condition/outcome instead)
6. Constraints MUST be Map/Object, NOT Array
7. Use empty arrays instead of fabricating non-existent entities
8. All 14 entity types supported (empty arrays OK)

**Source Code Specific Rules:**
1. PRESERVE exact naming - never rename classes, methods, variables
2. Extract SQL table/column names EXACTLY as written (case-sensitive)
3. For inferred business logic (no comments), use confidence 0.5-0.69
4. For documented business logic (JavaDoc, docstrings), use confidence 0.8-1.0
5. DO NOT extract test code as real business logic (check for @Test, test_, TestCase)

**Common Pitfalls to Avoid:**
1. ❌ Extracting generic utility methods as business capabilities (e.g., StringUtils, DateFormatter)
2. ❌ Treating test code as production business logic
3. ❌ Fabricating business purpose when only seeing technical implementation
4. ❌ Extracting framework code (Spring, Django internals) as business components
5. ❌ Confusing technical component (OrderService class) with business capability (Order Management)
6. ❌ Inventing database schema not present in CREATE TABLE or @Entity
7. ❌ Extracting commented-out code as active logic
