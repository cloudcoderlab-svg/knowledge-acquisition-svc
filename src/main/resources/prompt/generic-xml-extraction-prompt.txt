ENTITY MATCHING CRITERIA
===========================

When extracting entities from XML, match names with document context:

**Exact Match (use existing entity):**
- XML element/attribute name matches known entity (case-insensitive): <Component name="OrderService"> matches "OrderService" from known list
- Common variations: "Order-Service" = "OrderService" = "order_service"
- Abbreviations with context: "OrdSvc" = "OrderService" (if clearly the same from XML context)

**Create New Entity (different concept):**
- XML element name doesn't match any known entity
- Same name but different context/type indicates different entity

**Consistency:**
- Use the most complete/formal name when XML has multiple variations
- Prefer names matching document-level entities for linking
- When XML name matches known entity, use EXACT known name and increase confidence to 0.9+

===========================
CONFIDENCE SCORING RUBRIC
===========================

Assign confidence scores using these XML-specific criteria:

**0.9-1.0 (Very High):**
- XML element explicitly defined with multiple meaningful attributes
- All key information present and clear (name, type, description)
- Matches expected XML structure and document context
- Example: <Entity name="Customer" type="master" persistent="true"><Description>Customer master data</Description></Entity>

**0.7-0.89 (High):**
- XML element explicitly defined with some attributes
- Most key information present (at minimum: name or id)
- May not have all optional attributes
- Example: <Entity name="Customer" type="master"/> (name and type present, minimal description)

**0.5-0.69 (Medium):**
- XML element implied or minimally defined
- Only basic identification (name or id attribute)
- Inferred from parent-child structure or references
- Example: <Entity name="Customer"/> or <Reference target="Customer"/> (referenced but not defined)

**Below 0.5:**
- DO NOT extract - insufficient XML evidence
- Only tag name without meaningful attributes or child elements
- Highly speculative or uncertain

EDGE CASE HANDLING
===========================

**XML Namespaces:**
- <ns:Entity xmlns:ns="http://example.com"> → Use local name "Entity"
- Preserve namespace prefix in description if semantically significant
- Don't extract namespace URIs as entity names

**CDATA Sections:**
- <Description><![CDATA[Text with <special> chars]]></Description>
- Extract content: "Text with <special> chars"
- Don't include CDATA delimiters in extracted text

**Mixed Content:**
- <Description>Text <b>bold</b> more text</Description>
- Extract concatenated: "Text bold more text"
- Ignore formatting tags, preserve text content

**Empty Elements:**
- <Field name="status"/> → Extract with name only, use medium confidence (0.6-0.7)
- <Field/> → Omit (no meaningful attributes)

**Attribute vs Element Content:**
- Prioritize attributes for structured data: <Entity name="X" type="Y">
- Use element text content when attributes absent: <EntityName>CustomerMaster</EntityName>

**Inheritance & Extension:**
- <Entity name="Customer" extends="Party"> → Create "extends" relationship
- Don't duplicate parent attributes/children in child entity

**Comments & Processing Instructions:**
- <!-- Comment --> → Ignore XML comments unless containing critical metadata
- <?processing instruction?> → Ignore processing instructions

**Repeated Elements:**
- <Fields><Field name="id"/><Field name="name"/></Fields>
- Extract each <Field> as separate array entry in fields[]
- Use sequence/position for ordering when @sequence absent

**Ambiguous Element Purpose:**
- If unclear whether element is component, rule, or flow:
  - Use @type attribute as primary indicator
  - Use parent element context as secondary indicator
  - Use element name convention as tertiary indicator (e.g., "Service" → component)
  - When still ambiguous, choose most specific category and use medium confidence
