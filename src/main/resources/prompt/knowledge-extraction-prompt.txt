===========================
ANTI-HALLUCINATION RULES
===========================

CRITICAL - Follow these rules to prevent fabrication:

1. Extract ONLY information EXPLICITLY present in the content below
2. DO NOT infer entities, relationships, or fields beyond what is stated or directly implied
3. DO NOT fabricate business rationale, examples, or descriptions not in the source
4. PRESERVE exact entity names and terminology from the source without modification
5. DO NOT assume standard relationships - only extract relationships explicitly mentioned
6. If a field is not clearly present in content, OMIT it (do not guess or invent)
7. Use lower confidence scores (0.5-0.69) when information is partial or implied
8. DO NOT extract entities with only a name and no other supporting information
9. When uncertain about extraction validity, omit the entity rather than guessing

===========================
ENTITY MATCHING CRITERIA
===========================

When referencing entities, match names using these rules:

**Exact Match (use existing entity):**
- Identical names (case-insensitive): "OrderService" = "OrderService" = "orderservice"
- Common variations: "Order Service" = "OrderService" = "order-service"
- Abbreviations with context: "UserSvc" = "UserService" (if clearly the same)

**Create New Entity (different concept):**
- Different names with different meanings: "OrderService" ≠ "PaymentService"
- Same abbreviation, different context: "US" could be "UserService" or "United States"

**Consistency:**
- Use the most complete/formal name when multiple variations exist
- Prefer names matching document-level entity names for linking

===========================
CONFIDENCE SCORING RUBRIC
===========================

Assign confidence scores using these criteria:

**0.9-1.0 (Very High):**
- Entity explicitly mentioned AND described in detail
- All key fields present and clear
- Matches expected document context
- Example: "The OrderService component processes customer orders using REST APIs"

**0.7-0.89 (High):**
- Entity explicitly mentioned with some details
- Most key fields present
- May not fully align with document context
- Example: "OrderService handles orders" (mentioned but minimal detail)

**0.5-0.69 (Medium):**
- Entity implied or partially described
- Only basic fields present (name, type, minimal description)
- Inferred from context rather than explicit statement
- Example: Workflow mentioned but steps not detailed

**Below 0.5:**
- DO NOT extract - insufficient evidence
- Only name mentioned without context
- Highly speculative or uncertain

===========================
OUTPUT QUALITY RULES
===========================

1. **Field Inclusion:**
   - Omit optional fields if not present in content (don't use null or empty strings)
   - Use empty arrays [] only for collection fields when no items exist
   - Required fields for all entities: name field, type field (if applicable), confidence

2. **Minimum Extraction Criteria:**
   - Must have entity name + at least 2 other meaningful fields to extract
   - Entity with only name and confidence = insufficient, omit it
   - Prefer quality over quantity

3. **Field Population:**
   - Only populate fields with actual extracted information
   - Don't populate placeholder text or generic descriptions
   - Preserve source terminology in name fields

4. **Array Handling:**
   - Use empty array [] for top-level entity collections with no items
   - Omit empty nested arrays within entities (e.g., don't include empty "steps" array)

===========================
EDGE CASE HANDLING
===========================

**Abbreviations/Acronyms:**
- Extract full form if present: "BPM (Business Process Management)"
- If only abbreviation given with no definition, use abbreviation as name
- Add context in description if abbreviation meaning is implied

**Partial Information:**
- Extract entity if name + type + at least one other meaningful field present
- Use medium confidence (0.5-0.69) for partial extractions
- Omit fields that are not clearly present

**Conflicting Information:**
- If chunk contains conflicting data, extract the most recent or authoritative version
- Note conflict in description field if significant
- Use medium confidence when conflict exists

**Ambiguous Entities:**
- If unclear whether text describes one entity or multiple, favor single entity
- Use description field to capture ambiguity
- Medium confidence for ambiguous cases

**Lists and Enumerations:**
- When content lists multiple entities of same type, extract each separately
- Maintain original names from list
- Same confidence for all if list context is clear

===========================
ENTITY TYPE DESCRIPTIONS
===========================

**businessRoles:** Actors (human or system) that interact with processes - includes both organizational roles (Admin, Approver) and user personas (Premium Customer, Guest). Merged category replacing separate businessRoles/businessUsers.

**businessCapabilities:** What the organization does or can do to achieve goals - independent of how it's implemented (Customer Management, Order Processing).

**businessRules:** Validation, calculation, authorization, or policy rules that govern business logic.

**businessFlows:** Workflows, processes, or user journeys from trigger to outcome.

**businessDecisions:** Critical decision points in workflows where choices are made based on criteria.

**businessTerms:** Domain vocabulary and ubiquitous language - core business concepts and terminology.

**businessPolicies:** Governance rules, compliance requirements, operational policies.

**businessMetrics:** KPIs and performance indicators measuring capabilities or processes.

**solutionComponents:** Software modules, services, libraries, platforms implementing capabilities.

**apis:** API endpoints, web services, or interfaces for system integration.

**deploymentResources:** Infrastructure components - servers, databases, cloud resources.

**dataModels:** Data structures, entities, tables, or documents representing business concepts.

**integrations:** Data or event exchanges between systems.

**knowledgeNotes:** Miscellaneous insights, decisions, constraints, or recommendations not fitting other categories.

===========================
RELATIONSHIP TYPES (19)
===========================

Use these relationship types based on context:

**Dependency & Invocation:**
- **depends_on:** Component/workflow requires another to function
- **calls:** Component invokes API or service
- **uses:** General usage or consumption of a resource

**Data Flow:**
- **sends_to:** Sends data/messages to target
- **receives_from:** Receives data/messages from source
- **reads_from:** Reads data from source (database, file, API)
- **writes_to:** Writes data to target (database, file, API)
- **stores_in:** Persists data in target storage
- **publishes:** Publishes events/messages to topic/queue
- **subscribes:** Subscribes to events/messages from topic/queue

**Structure & Inheritance:**
- **implements:** Implements interface, specification, or design
- **extends:** Extends or inherits from parent
- **contains:** Parent contains child component/module

**Processing:**
- **triggers:** Initiates or starts target workflow/process
- **validates:** Validates data or business rule
- **transforms:** Transforms data from one format to another

**Business Relationships:**
- **approves:** Role approves decision/workflow step
- **owns:** Role or team owns capability/component
- **measured_by:** Capability measured by metric
